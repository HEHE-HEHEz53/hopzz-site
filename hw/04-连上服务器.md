# 04 连上服务器：设备怎么和 hopzz.top 通信

这一篇讲清楚四件事：

1. 设备发什么、发到哪里、服务端怎么回（**API 契约，不能改**）。
2. 设备令牌（device token）是什么，为什么不能泄露。
3. HTTPS 证书校验到底在验什么，ESP32 为什么会被“时间”卡住。
4. 失败了怎么重试，多久上报一次，怎么在网页上显示最新数据。

服务端由 Lead 按下面的契约实现。**你不需要改服务端，也不要在设备端改字段名、路径、请求头。** 你只需要把设备端代码里的 WiFi、令牌填对。

> 当前服务端已经上线，浏览器打开 `https://hopzz.top/api/docs` 可以直接点 “Try it out” 测试接口；打开 `https://hopzz.top` 可以看到个人主页。设备端仍按下面的契约写，不受影响。

## 一、整体通信流程

```text
┌──────────┐        ［1］连 2.4G WiFi         ┌────────┐
│  ESP32   │ ───────────────────────────────> │ 路由器  │
│          │                                  └────┬───┘
│          │        ［2］HTTPS POST                │
│          │  https://hopzz.top/api/telemetry      │
│          │  Header: X-Device-Token: ****         │
│          │  Body: {"device_id":...}              │
│          │ ────────────────────────────────> ┌───▼──────────┐
│          │                                  │ VPS           │
│          │        ［3］200 {"ok":true}        │ hopzz.top     │
│          │ <──────────────────────────────── │ 写入数据库     │
└──────────┘                                  └───┬──────────┘
                                                  │
                                      ［4］GET /api/telemetry/latest
                                                  │（只读，无需令牌）
                                            ┌─────▼─────┐
                                            │ 个人主页   │
                                            │ 显示最新值 │
                                            └───────────┘
```

设备只做两件事：**POST 上报**、**失败重试**。网页只做一件事：**GET 最新数据**。

## 二、API 契约（严格按这个来）

### 2.1 上报接口

```http
POST https://hopzz.top/api/telemetry
Content-Type: application/json
X-Device-Token: <设备令牌>

{"device_id":"esp32-01","temperature":26.5,"humidity":58.2}
```

| 项目 | 值 | 说明 |
|---|---|---|
| 方法 | `POST` | 不是 GET，不是 PUT |
| 地址 | `https://hopzz.top/api/telemetry` | 必须 HTTPS；不要改成 `http://`，不要加结尾斜杠 |
| 请求头 1 | `Content-Type: application/json` | 告诉服务端 body 是 JSON |
| 请求头 2 | `X-Device-Token: <设备令牌>` | 设备身份凭证，**不是** `Authorization: Bearer` |
| 请求体 | `{"device_id":"esp32-01","temperature":26.5,"humidity":58.2}` | 字段名、大小写、类型都不能改 |
| 成功响应 | `200` + `{"ok":true}` | 设备以状态码 `200` 为准；当前服务端还会附带 `created_at`，不影响 |
| 令牌错误 | `401` | 令牌缺失/不匹配 |
| 字段缺失 | `422` | 缺字段、字段类型不对、JSON 不合法等 |

> 当前服务端的成功响应实际形如 `{"ok":true,"created_at":"2026-11-01 09:30:00"}`。契约要求的是 `{"ok":true}`，多出来的 `created_at` 是正常附加信息，设备不用解析。

**字段要求：**

| 字段 | 类型 | 示例 | 注意 |
|---|---|---|---|
| `device_id` | 字符串 | `"esp32-01"` | 必须有引号；多台设备要不同 |
| `temperature` | 数字 | `26.5` | **不能加引号**；单位摄氏度 |
| `humidity` | 数字 | `58.2` | **不能加引号**；单位 %RH |

JSON 的细节：

- 用**英文双引号**，不要用中文引号 `“”`。
- 最后一个字段后面**不能有逗号**。
- 数字不要写成 `"26.5"`；布尔值不要写成 `"true"`。
- 整个 body 是一行也可以，格式化也可以，服务端解析的是 JSON，不是看空格。
- **设备端始终发完整的 `device_id` + `temperature` + `humidity`。** 不要只发其中一个测量值；契约要求这两个字段，服务端也可能按更严格的规则校验。

### 2.2 读取最新数据接口

```http
GET https://hopzz.top/api/telemetry/latest
```

| 项目 | 值 |
|---|---|
| 方法 | `GET` |
| 地址 | `https://hopzz.top/api/telemetry/latest` |
| 令牌 | **不需要**（只读公开接口） |
| 返回 | 当前实现：`200` + `{"ok":true,"latest":{...}}`；还没有数据时 `latest` 为 `null` |

> **返回 JSON 的实际形状（当前服务端）：**
>
> ```json
> {"ok":true,"latest":{"device_id":"esp32-01","temperature":26.5,"humidity":58.2,"extra":null,"created_at":"2026-11-01 09:30:00"}}
> ```
>
> 没有数据时：
>
> ```json
> {"ok":true,"latest":null}
> ```
>
> 下面的网页示例优先读 `latest`，同时兼容 `data` 或“直接返回数据对象”的形式。**以服务端实际返回为准，不要改 API 契约。**

### 2.3 用 curl 先测服务端（不要一上来就烧代码）

在电脑或 VPS 上，先用 `curl` 测一遍。把 `<设备令牌>` 换成真实令牌（**不要发到群里/截图里**）。

**测试成功上报：**

```bash
curl -i -X POST https://hopzz.top/api/telemetry \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: <设备令牌>" \
  -d '{"device_id":"esp32-01","temperature":26.5,"humidity":58.2}'
```

期望：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"ok":true,"created_at":"2026-11-01 09:30:00"}
```

契约要求 body 至少包含 `{"ok":true}`；当前服务端会多一个 `created_at`，正常。

**测试令牌错误：**

```bash
curl -i -X POST https://hopzz.top/api/telemetry \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: wrong-token" \
  -d '{"device_id":"esp32-01","temperature":26.5,"humidity":58.2}'
```

期望 `401`。如果 wrong-token 也返回 200，说明服务端没校验令牌，要找 Lead。

**测试字段缺失（只发 device_id，温度和湿度都不发）：**

```bash
curl -i -X POST https://hopzz.top/api/telemetry \
  -H "Content-Type: application/json" \
  -H "X-Device-Token: <设备令牌>" \
  -d '{"device_id":"esp32-01"}'
```

期望 `422`。设备代码始终会发完整的 `temperature` 和 `humidity`，不要只发一个字段。

**测试读取最新：**

```bash
curl -i https://hopzz.top/api/telemetry/latest
```

期望 `200`，body 形如 `{"ok":true,"latest":{...}}`。还没有硬件上报过时，返回 `{"ok":true,"latest":null}`，这也是正常的，不是报错。如果返回 `404`，才是路由没部署或路径写错，先确认服务端状态。

> Windows PowerShell 里如果 `curl` 被别名成 `Invoke-WebRequest`，用 `curl.exe` 代替，或者用 Git Bash 执行上面的命令。PowerShell 里单引号包 JSON 通常没问题；如果转义麻烦，就把 JSON 写进文件再用 `--data @body.json`。

**先让 curl 通过，再烧设备。** 如果 curl 都 401/422/404，设备端再怎么重试也没用。

## 三、设备令牌（device token）到底是什么

### 3.1 它是什么

设备令牌是**服务端生成的一串随机字符串**，用来回答一个问题：

> “这个请求，真的是我允许的那台设备发来的吗？”

它相当于设备的“门禁卡”：

- 服务端生成，交给设备；
- 设备每次 POST 都放在 `X-Device-Token` 请求头里；
- 服务端核对：令牌存在、没被吊销、对应哪台设备；
- 对不上就返回 `401`。

它**不是**：

- 不是 WiFi 密码；
- 不是你的网站登录密码；
- 不是 `device_id`（`device_id` 是公开的名字，令牌才是秘密）；
- 不是可以随便猜的“123456”。

### 3.2 令牌怎么用

在 [code/03_post_to_server.ino](code/03_post_to_server.ino) 顶部：

```cpp
#define DEVICE_TOKEN "把服务器给你的设备令牌填在这里"
```

把引号里的内容替换成服务端给你的令牌，例如：

```cpp
#define DEVICE_TOKEN "3f9c2a7e-1b2c-4d5e-8f90-123456789abc"
```

然后重新上传。

### 3.3 令牌的规矩

- **一个设备一个令牌。** 以后加第二块 ESP32，让服务端再生成一个，不要共用。当前服务端先按一台设备配置，扩展时再让 Lead 加。
- **不要提交到公开 GitHub。** 代码里先放占位符；真正令牌可以放在不提交的 `secrets.h` 里（进阶做法），或者上传前手动填。
- **不要放在 URL 查询参数里。** 例如 `?token=...` 会进服务器日志、浏览器历史；契约要求放请求头。
- **不要发到群里、截图里、聊天记录里。** 泄露了就让服务端吊销/重置。
- **令牌走 HTTPS 才是加密的。** 如果用 HTTP，令牌在网络上明文传输，等于没有。
- 令牌泄露的后果：别人可以冒充你的设备发假数据。一般不能直接控制你的继电器（继电器在本地），但会污染数据。

### 3.4 令牌错了怎么办

串口看到：

```text
401：设备令牌不对，检查 DEVICE_TOKEN 是否和服务端一致
```

按顺序查：

1. 代码里的 `DEVICE_TOKEN` 是不是服务端给的那个，有没有多空格、少字符、引号是不是英文。
2. 服务端是不是把令牌存在环境变量/配置文件里，实际值和你以为的不一样。
3. 服务端有没有把令牌和 `device_id` 绑定；`device_id` 写错也可能被拒。
4. 让 Lead 在服务端日志里看这个请求到底带没带 `X-Device-Token`。

## 四、HTTPS 证书校验：ESP32 最容易卡住的地方

### 4.1 HTTPS 到底多了什么

HTTP 是明文；HTTPS 是 HTTP 外面套了一层 **TLS**（Transport Layer Security，传输层安全）。TLS 做两件事：

1. **加密**：中间人看不到你发的内容（包括令牌和温湿度）。
2. **认证**：客户端确认“对面真的是 hopzz.top”，不是冒充的服务器。

认证靠**证书**（certificate）：

- 服务器出示证书；
- 证书由**证书颁发机构（CA，Certificate Authority）**签名；
- 客户端用内置/配置的**根证书（root CA）**去验证签名链；
- 还要检查证书里的**域名**是不是 `hopzz.top`；
- 还要检查**当前时间**是否在证书有效期内。

任何一项不对，TLS 握手就失败。

### 4.2 ESP32 的特殊问题：它没有电就开始“1970 年”

ESP32 没有带电池的 RTC（实时时钟）。刚上电时，系统时间通常是：

```text
1970-01-01 00:00:00 UTC
```

而服务器证书的有效期是比如 `2026-02-01` 到 `2027-01-30`。ESP32 一看“现在是 1970 年”，就会认为证书**还没生效**，于是拒绝连接。

**所以：**

- 用 `client.setInsecure()`：跳过证书校验，1970 年也能连。**这是本教程第一版代码的做法，仅用于跑通。**
- 用 `client.setCACert(...)`：必须先把时间同步正确（NTP），否则一定失败。

### 4.3 `setInsecure()`：能跑通，但不安全

`03_post_to_server.ino` 里现在是：

```cpp
client.setInsecure();
```

它的意思是：**“别验证证书了，直接加密连接。”**

- 好处：ESP32 不用管时间，第一次联调最容易成功。
- 坏处：不验证服务器身份。如果 DNS 被污染、或者有人冒充 `hopzz.top`，ESP32 会把令牌和数据发给假服务器。
- 适用：**只在你自己家/实验室第一次调试时用。**
- 不适用：长期运行、公网、涉及令牌的项目。

**跑通之后，生产环境要改成 `setCACert()`。** 下面给做法。

### 4.4 生产做法：NTP 对时 + 根证书

#### 第一步：连上 WiFi 后同步时间

```cpp
#include <time.h>

void syncTime() {
  // 参数：时区偏移（秒）、夏令时偏移（秒）、NTP 服务器 1、NTP 服务器 2
  // 0, 0 表示 UTC；证书校验只关心绝对时间，不关心本地时区。
  configTime(0, 0, "pool.ntp.org", "time.cloudflare.com");

  Serial.print("等待 NTP 对时");
  unsigned long startMs = millis();
  time_t now = time(nullptr);

  // 1700000000 约等于 2023-11-14。
  // 大于它只说明“时间不再是 1970 年”，真正的当前时间由 NTP 给。
  while (now < 1700000000 && (millis() - startMs) < 20000) {
    delay(500);
    Serial.print(".");
    now = time(nullptr);
  }
  Serial.println();

  if (now < 1700000000) {
    Serial.println("NTP 对时失败：检查网络是否允许 UDP 123，或换 NTP 服务器");
  } else {
    Serial.print("NTP 对时成功，时间戳: ");
    Serial.println((unsigned long)now);
  }
}
```

注意：

- NTP 用的是 **UDP 123** 端口。有些公司/校园网会封 UDP，导致对时失败；家里网络一般没问题。
- `configTime` 只是“开始同步”，要**循环等** `time(nullptr)` 变成合理值，不能调用完立刻发 HTTPS。
- 时区参数填 `0, 0`（UTC）就够证书校验用；如果你想串口打印北京时间，再单独设置时区。

#### 第二步：把根证书放进代码

```cpp
// 把根证书的 PEM 内容原样放进来（包括 BEGIN/END 行）
const char* ROOT_CA = R"EOF(
-----BEGIN CERTIFICATE-----
这里放根证书的 Base64 内容
-----END CERTIFICATE-----
)EOF";
```

`R"EOF(... )EOF"` 是 C++ 的**原始字符串**（raw string），里面的反斜杠、换行不会被转义，适合放 PEM。

#### 第三步：替换 `setInsecure()`

```cpp
// 先对时
syncTime();

WiFiClientSecure client;
client.setCACert(ROOT_CA);   // 用根证书验证服务器

HTTPClient https;
if (!https.begin(client, SERVER_HOST, TELEMETRY_PORT, TELEMETRY_PATH, true)) {
  ...
}
```

这样 TLS 会验证：

- 证书链能不能追到你给的根 CA；
- 证书里的域名是不是 `hopzz.top`；
- 当前时间在不在有效期内。

#### 根证书从哪里来

不要凭记忆手写。常见做法：

1. 在 VPS 或本地用 OpenSSL 看服务器证书链：

   ```bash
   openssl s_client -connect hopzz.top:443 -servername hopzz.top -showcerts
   ```

   输出的最上面是服务器证书（leaf），中间是中间证书（intermediate）。**根证书通常不在服务器发送的链里**，需要从 CA 官方或系统证书库获取。

2. 如果站点用 **Let's Encrypt**，根证书常见是 **ISRG Root X1**（RSA）或 **ISRG Root X2**（ECDSA）。以实际证书链为准，不要想当然。确认是 X1 时，官方 PEM 地址是 `https://letsencrypt.org/certs/isrgrootx1.pem`；X2 则是 `https://letsencrypt.org/certs/isrgrootx2.pem`。
3. 让 Lead 直接给你“服务器证书链对应的根 CA PEM”，这是最省事的。
4. 如果站点用的是自签名证书（不推荐生产），就把那张自签名证书作为 CA 传给 `setCACert`。

#### 证书更新怎么办

- **不要 pin 服务器叶子证书**。Let's Encrypt 证书通常 90 天续期一次，一换证书设备就连不上。
- **pin 根证书**更稳，根证书通常很多年不变。
- 如果服务端换了 CA，设备要重新烧根证书。

#### 常见 TLS 失败原因

| 现象 | 原因 | 怎么修 |
|---|---|---|
| `setCACert` 后连不上，串口负数错误 | 时间还是 1970 | 先 `syncTime()`，确认 `time(nullptr)` 合理 |
| 时间对了还失败 | 根证书不对/不全 | 用实际证书链的根 CA；检查 PEM 的 BEGIN/END 行 |
| 之前能连，续期后失败 | pin 了叶子证书 | 改成根证书，不要 pin 叶子 |
| 换 WiFi 后失败 | 新网络封 UDP 123 / 需要认证 | 换网络；或先用 `setInsecure` 确认是时间问题 |
| 浏览器正常，ESP32 失败 | ESP32 根证书库/时间/SNI 问题 | 用域名不用 IP；先 `setInsecure` 排除网络，再逐步换 CA |

### 4.5 一句话总结

> **测试阶段用 `setInsecure()` 先跑通；生产环境用“NTP 对时 + 根证书 `setCACert()`”；不要长期用 `setInsecure()`。**

## 五、上报间隔、超时和重试

### 5.1 上报间隔

`03_post_to_server.ino` 默认：

```cpp
#define REPORT_INTERVAL_MS 30000UL   // 30 秒
```

建议：

| 场景 | 间隔 | 说明 |
|---|---|---|
| 第一次联调 | 30 秒 | 方便看日志，服务器压力也不大 |
| 长期室温监测 | 1～5 分钟 | 温湿度变化慢，没必要 30 秒一条 |
| 多台设备 | 5 分钟 + 随机抖动 | 避免所有设备同一秒一起发 |
| 电池供电 | 5～15 分钟 + 深睡眠 | 需要改代码用 deep sleep，本教程不展开 |

DHT22 本身最快约 2 秒一次，但**不要**按 2 秒上报：服务器写入、数据库、网页刷新都不需要这么密。30 秒～5 分钟是合理范围。

### 5.2 超时

```cpp
#define HTTP_TIMEOUT_MS 10000   // 10 秒
```

- TLS 握手 + DNS + 服务器处理，正常 1～3 秒；网络差可能 5 秒。
- 不要设 2 秒，容易把正常的慢请求误判为失败。
- 也不要设 60 秒，WiFi 断了会卡很久。

### 5.3 重试策略

`03` 里的逻辑：

```text
200        -> 成功，结束
401        -> 令牌错，重试没用，直接放弃
422        -> 字段/格式错，重试没用，直接放弃
网络错误    -> 1s、2s、4s 退避，最多 3 次
5xx / 429  -> 同上，退避重试
```

为什么 401/422 不重试？因为它们是**确定性错误**：令牌不会因为多试几次就变对，字段也不会自己长出来。重试只会浪费电、刷日志。

为什么 5xx 要重试？服务器临时故障、数据库锁、重启，过几秒可能就好了。

生产环境可以再加：

- **随机抖动（jitter）**：`delay(backoff + random(0, 1000))`，避免大量设备同时重试。
- **最大退避上限**：比如最多 60 秒。
- **失败计数/告警**：连续失败 10 次，点亮红灯或上报状态。
- **本地缓存**：断网时把最近几条存到 RTC/Flash，恢复后补发。新手先不做。

### 5.4 状态码速查

| 状态码 | 含义 | 设备该怎么做 |
|---|---|---|
| `200` | 成功 | 继续下一轮 |
| `3xx` | 重定向 | 检查 `www`/路径；当前设备代码不跟随重定向 |
| `400` | 请求格式错（契约外） | 检查 JSON；不要盲目重试 |
| `401` | 令牌错/缺失 | 改 `DEVICE_TOKEN`，不要重试 |
| `404` | 路径错/路由没部署 | 检查 URL；找 Lead |
| `405` | 方法错（用了 GET/PUT） | 改成 POST |
| `422` | 字段缺失/类型错 | 检查 JSON 字段 |
| `408` | 请求超时 | 退避后重试 |
| `429` | 请求太频繁 | 退避，降低上报频率 |
| `500`/`502`/`503` | 服务端临时故障 | 退避重试 |
| 负数 | 本地网络/TLS 错误 | 检查 WiFi、时间、证书、DNS |

## 六、在网页上显示最新数据

### 6.1 最简方式：浏览器直接打开

先确认接口通：

```text
https://hopzz.top/api/telemetry/latest
```

浏览器能打开、能看到 JSON，说明 GET 接口正常。当前个人主页已经接好了这个接口，设备上报成功后刷新主页就能看到最新温湿度；下面这个 `latest.html` 是**独立的最小示例**，用来理解原理或单独测试。

### 6.2 一个可用的最小页面

把下面内容保存成 `latest.html`，放到网站同源目录（例如站点根目录），通过 `https://hopzz.top/latest.html` 访问。**不要用 `file://` 直接双击打开**，否则 `fetch` 的路径和跨域规则不一样。

```html
<!doctype html>
<html lang="zh-CN">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>最新温湿度</title>
  <style>
    body { font-family: system-ui, sans-serif; max-width: 640px; margin: 48px auto; padding: 0 16px; }
    .card { border: 1px solid #ddd; border-radius: 12px; padding: 24px; }
    .value { font-size: 2rem; font-weight: 700; }
    .muted { color: #666; font-size: 0.9rem; }
    pre { background: #f6f6f6; padding: 12px; overflow: auto; }
  </style>
</head>
<body>
  <h1>最新温湿度</h1>
  <div class="card">
    <div>温度：<span class="value" id="temp">--</span> °C</div>
    <div>湿度：<span class="value" id="hum">--</span> %RH</div>
    <p class="muted" id="meta">等待数据...</p>
    <p class="muted" id="status"></p>
  </div>
  <h2>原始返回</h2>
  <pre id="raw">--</pre>

  <script>
    async function refresh() {
      const statusEl = document.getElementById('status');
      try {
        // 相对路径：页面和 API 同源时最省事，不会触发跨域。
        const res = await fetch('/api/telemetry/latest', { cache: 'no-store' });
        if (!res.ok) throw new Error('HTTP ' + res.status);

        const json = await res.json();

        // 当前服务端返回：{"ok":true,"latest":{...}} 或 {"ok":true,"latest":null}
        // 同时兼容 {"ok":true,"data":...} 和直接返回数据对象的写法。
        let d;
        if (json && json.latest !== undefined) {
          d = json.latest;
        } else if (json && json.data !== undefined) {
          d = json.data;
        } else {
          d = json;
        }
        if (Array.isArray(d)) d = d[0] || {};

        if (!d) {
          // latest 为 null：还没有硬件上报过，这不是错误。
          document.getElementById('temp').textContent = '--';
          document.getElementById('hum').textContent = '--';
          document.getElementById('meta').textContent = '还没有硬件上报数据';
          document.getElementById('raw').textContent = JSON.stringify(json, null, 2);
          statusEl.textContent = '更新于 ' + new Date().toLocaleTimeString();
          return;
        }

        document.getElementById('temp').textContent =
          (d.temperature !== undefined) ? d.temperature : '--';
        document.getElementById('hum').textContent =
          (d.humidity !== undefined) ? d.humidity : '--';

        // 不同服务端可能用 created_at / timestamp / time，按实际字段显示。
        const when = d.created_at || d.timestamp || d.time || '';
        const who = d.device_id || '';
        document.getElementById('meta').textContent =
          [who, when].filter(Boolean).join(' · ') || '已获取最新数据';

        document.getElementById('raw').textContent = JSON.stringify(json, null, 2);
        statusEl.textContent = '更新于 ' + new Date().toLocaleTimeString();
      } catch (e) {
        statusEl.textContent = '读取失败：' + e.message;
      }
    }

    refresh();
    setInterval(refresh, 30000); // 每 30 秒刷新一次
  </script>
</body>
</html>
```

说明：

- 页面**不包含设备令牌**。GET 最新数据是只读公开接口，不需要令牌；把令牌写进前端 JS 等于公开。
- 当前服务端返回 `{"ok":true,"latest":{...}}`，页面优先读 `latest`；没有数据时 `latest` 为 `null`，页面会显示“还没有硬件上报数据”。
- 用 `textContent` 而不是 `innerHTML` 写数据，避免 JSON 里的内容被当成 HTML 执行。
- `fetch('/api/telemetry/latest')` 是相对路径，要求页面和 API **同源**（都在 `https://hopzz.top`）。
- 如果页面在 `https://www.hopzz.top`，API 在 `https://hopzz.top`，就是跨域（CORS）。最省事的做法是把页面放到 `hopzz.top` 同源下；否则要让服务端加 CORS 响应头。
- 页面每 30 秒刷新一次；设备也是 30 秒上报，网页可能看到“同一条数据”两次，正常。
- 如果服务端返回的字段名不是 `temperature` / `humidity`，改页面里的取值；**不要改 API 契约**，先看实际返回。

### 6.3 如果页面显示 404 / CORS 错误

| 现象 | 原因 | 怎么修 |
|---|---|---|
| `HTTP 404` | 路由没部署 / 路径写错 | 先用 curl 测；找 Lead 确认 |
| `Failed to fetch` / CORS | 页面和 API 不同源 | 页面放同源；或服务端加 CORS |
| 页面能打开但值一直是 `--` | 返回字段名不同/没有数据 | 看“原始返回”；按实际字段改 |
| `Mixed Content` | 页面是 https，请求写成 http | 全部用 https/相对路径 |

## 七、完整联调顺序（照着做）

1. **服务端先自测**：`curl` POST 成功、401、422、GET latest 都符合预期。
2. **设备连 WiFi**：串口打印 `WiFi 已连接，IP: ...`。
3. **设备读传感器**：串口有合理温湿度，不是 `NaN`。
4. **设备上报**：串口打印 `HTTP 状态码: 200`、`服务器响应: {"ok":true,...}`、`上报成功`。
5. **服务端确认**：网页/数据库/日志能看到 `esp32-01` 的新记录。
6. **网页读取**：浏览器打开 `/api/telemetry/latest` 有数据；再打开你的页面。
7. **稳定性观察**：放 30 分钟，看是否重启、是否 401/422、是否重复上报。
8. **改生产配置**：换 NTP + 根证书，去掉 `setInsecure()`；调整上报间隔；给设备加外壳。

## 八、安全检查清单

- [ ] 用的是 `https://`，不是 `http://`。
- [ ] 设备令牌只出现在 `X-Device-Token` 请求头，不在 URL、不在前端 JS。
- [ ] 令牌没有提交到公开仓库。
- [ ] 生产环境不用 `setInsecure()`，改成 NTP + 根证书。
- [ ] 根证书不是服务器叶子证书；没有 pin 90 天就过期的叶子证书。
- [ ] 网页只读接口不返回敏感信息（目前只有温湿度，可以公开）。
- [ ] 服务器 401/422 的日志没有把完整令牌打印出来。
- [ ] 设备令牌泄露时知道怎么让服务端吊销/重置。

## 九、你可能会问

**Q：为什么不用 MQTT？**  
A：MQTT 更适合大量设备、双向控制、低带宽。你现在只有一台设备、一个网站，HTTPS POST 足够简单，服务端也不用额外跑 broker。以后设备多了再考虑。

**Q：为什么设备不直接写数据库？**  
A：数据库不应该暴露给公网设备。设备只认 HTTPS API，API 后面怎么存、怎么鉴权，是服务端的事。这样换数据库、加限流都不用改设备。

**Q：为什么响应是 `{"ok":true}` 而不是数据？**  
A：上报接口只需要确认“收到了”。设备不需要服务器把数据再回传一遍；要读数据用 `GET /api/telemetry/latest`。

**Q：能不能用 `http://` 省掉证书麻烦？**  
A：不能。令牌会明文传输，任何人都能抓包冒充设备。TLS 的麻烦是一次性的，令牌泄露的麻烦是长期的。

**Q：ESP32 时间不对，除了 `setInsecure()` 还有别的办法吗？**  
A：有，就是 NTP 对时 + 根证书。`setInsecure()` 只是让你先跑通，不是最终方案。见第四节。

**Q：上报失败会丢数据吗？**  
A：会。当前代码失败就等下一轮，不缓存历史数据。学习项目可以接受；要补数据，需要自己加本地缓存（RTC/Flash）和补发逻辑。
