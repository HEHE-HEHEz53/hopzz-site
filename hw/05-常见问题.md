# 05 常见问题：现象 → 原因 → 怎么修

这篇是“救命文档”。遇到问题先在这里按现象找，不要急着重买板子。

排查顺序建议固定成一条线：

```text
电源/线材 → 串口能不能看到板子 → 代码能不能上传 → 传感器能不能读数
→ WiFi 能不能连 → HTTPS 能不能通 → 服务端返回什么 → 网页能不能显示
```

**一次只改一个变量。** 不要一边换线、一边改代码、一边重启路由器；那样即使修好了，你也不知道是哪一步修好的。

---

## 1. 插上板子，电脑没有 COM 口 / 显示“未知设备”

**现象：**

- 设备管理器里没有“端口（COM 和 LPT）”，或者只有一个带黄色感叹号的“未知设备”。
- 板子电源灯可能亮，也可能不亮。
- Arduino IDE 的“端口”菜单是灰的。

**原因（按概率排）：**

1. **USB 线是“只能充电”的线**，里面没有数据线芯。这是最常见的原因。
2. 电脑没有装 CP2102 / CH340 的 USB 转串口驱动。
3. USB 口坏了、USB 集线器供电不足、线接触不良。
4. 板子的 USB 座虚焊/损坏。
5. 板子进了奇怪的启动模式（少见）。

**怎么修：**

1. **换一条确定能传数据的 USB 线**（比如能给手机传文件的那条），直接插电脑主板后面的 USB 口，不要经过 Hub。
2. 看板子电源灯：
   - 不亮：先换线、换口、换电脑；还不亮，板子可能坏了。
   - 亮但没 COM：继续下一步。
3. 打开设备管理器，看“其他设备”里有没有带感叹号的项：
   - `CP2102 USB to UART Bridge` → 装 Silicon Labs 的 CP210x VCP 驱动。
   - `USB-SERIAL CH340` → 装沁恒（WCH）的 CH341SER 驱动。
   - 完全没反应 → 线/口/板子的问题。
4. 装完驱动**重新插拔**板子；还不行就重启电脑。
5. 换一台电脑试。如果另一台能识别，说明是你这台电脑的驱动/口问题。
6. 板子有 **BOOT** 和 **EN** 键的话：按住 BOOT，点一下 EN，再松开 BOOT，看设备管理器有没有反应（这会强制进下载模式）。

> 不要从“驱动大全”网站下不明 exe。CP210x 找 Silicon Labs，CH340 找 WCH 官网。

## 2. 上传失败：`Failed to connect to ESP32` / `Timed out waiting for packet header`

**现象：**

```text
Connecting........_____....._____
A fatal error occurred: Failed to connect to ESP32:
Timed out waiting for packet header
```

或者：

```text
Failed to connect to ESP32: No serial data received.
```

**原因：**

1. 板子没有进入**下载模式**（download mode）。有些板子的自动复位电路不灵。
2. 串口监视器还开着，COM 口被占用。
3. 端口选错（选成了蓝牙串口/别的设备）。
4. 开发板型号选错（比如买的是 ESP32-S3，却选了 ESP32 Dev Module）。
5. USB 线质量差、USB Hub 供电不足。
6. 上传速度太高。

**怎么修：**

1. **手动进下载模式**（最有效）：
   - 按住 **BOOT** 键不松；
   - 点 IDE 的上传按钮；
   - 看到 `Connecting...` 后松开 BOOT；
   - 上传完成后按一下 **EN** 复位。
2. **关掉串口监视器**再上传。Windows 上 COM 口是独占的。
3. `工具 → 端口` 选对 COM 口；把别的串口设备拔掉，避免选错。
4. `工具 → 开发板` 选对型号；不确定就拍板子照片查丝印上的芯片型号。
5. 上传速度从 `921600` 降到 `115200`。
6. 换短一点、粗一点的 USB 数据线，直插电脑。
7. Linux 下如果报权限错误，把用户加到 `dialout` 组，重新登录。

## 3. 串口全是乱码

**现象：**

串口监视器里是：

```text
�@�x��...
```

或者一堆问号/方块。

**原因：**

1. 串口监视器波特率和代码里的 `Serial.begin()` 不一致。
2. 选错了 COM 口（看的是别的设备）。
3. 板子上电最初几行是 ROM 启动日志，可能本来就是乱码，之后才正常。
4. USB 线/接口接触不良，数据传输出错。

**怎么修：**

1. 代码里写的是 `Serial.begin(115200)`，串口监视器右下角就选 **115200**。两边必须一样。
2. 按一下板子的 **EN** 键复位，观察是不是只有最开始几行乱、后面正常。如果后面正常，不用管。
3. 关掉串口监视器，重新选端口，再打开。
4. 换 USB 线/口。
5. 如果你改过代码里的波特率（比如 9600），串口监视器也要跟着改。

> ESP32 的 ROM 启动日志默认通常是 115200；如果你看到的是全程乱码，优先怀疑波特率或端口，不要先怀疑板子坏。

## 4. WiFi 连不上，或者连上了但发不出请求

**现象：**

- 串口一直打印 `......`，最后 `WiFi 连接超时`。
- 或者 `WiFi.status()` 是 `WL_NO_SSID_AVAIL` / `WL_CONNECT_FAILED`。
- 或者连上了，但 HTTPS 请求超时。

**原因：**

1. **ESP32-WROOM-32 只支持 2.4GHz WiFi，不支持 5GHz。** 这是头号原因。
2. 路由器把 2.4G 和 5G 合成同一个 SSID，设备被“带”到 5G 频段，连不上。
3. WiFi 密码错、SSID 有中文/特殊字符、隐藏 SSID。
4. 路由器开了 MAC 地址过滤、WPA3-only、家长控制。
5. 信号太弱、距离太远、路由器信道/兼容性问题。
6. 需要网页认证的公共 WiFi（captive portal），ESP32 没法点“同意”。

**怎么修：**

1. 进路由器后台，确认有独立的 **2.4GHz** WiFi；把 2.4G 和 5G 的 SSID 分开命名（例如 `home-2.4g` / `home-5g`），让 ESP32 连 2.4G 那个。
2. 用手机开一个 **2.4GHz 热点**（iPhone 的“个人热点”有的默认 5G，需在设置里开“最大兼容性”；安卓一般可设 2.4G），把代码里的 SSID/密码改成热点，测试是不是路由器问题。
3. 检查密码大小写、空格；SSID 先用纯英文数字。
4. 关掉路由器的 MAC 过滤/WPA3-only，或改成 WPA2/WPA3 混合。
5. 把路由器隐藏 SSID 关掉（ESP32 连隐藏 SSID 可能不稳定）。
6. 在代码里打印状态码，定位问题：

   ```cpp
   Serial.print("WiFi status: ");
   Serial.println(WiFi.status());
   ```

   常见值：

   | 值 | 含义 |
   |---|---|
   | `WL_IDLE_STATUS` (0) | 空闲/正在处理 |
   | `WL_NO_SSID_AVAIL` (1) | 没扫到这个名字的 WiFi |
   | `WL_SCAN_COMPLETED` (2) | 扫描完成 |
   | `WL_CONNECTED` (3) | 已连接 |
   | `WL_CONNECT_FAILED` (4) | 连接失败（密码/认证） |
   | `WL_CONNECTION_LOST` (5) | 连接丢失 |
   | `WL_DISCONNECTED` (6) | 已断开 |

7. 连上但请求超时：先 `ping hopzz.top`，再用电脑 `curl -v https://hopzz.top/api/telemetry/latest`，确认不是服务器/网络问题。

## 5. DHT22 一直读 `NaN`

**现象：**

```text
读取失败：返回 NaN，请检查接线、上拉电阻和传感器型号
```

**原因：**

1. 三根线接错/接触不良：VCC、DATA、GND 有一个没接好。
2. DATA 没接 `GPIO4`，或者代码里的 `DHT_PIN` 和实际不一致。
3. 裸的 4 针 DHT22 没加 **4.7k～10k 上拉电阻**。
4. 代码里 `DHT_TYPE` 写成了 `DHT11`，实际是 DHT22。
5. 读得太快，两次之间没有 2 秒。
6. 传感器坏了，或者买到了假 DHT22。
7. 线太长、接触电阻大、电源不稳。

**怎么修：**

1. 断电，重新插一遍三根线；用手轻拉一下，确认不松。
2. 用万用表量模块 VCC 对 GND 是不是约 3.3V；量 DATA 对 GND 在空闲时是不是接近 3.3V（上拉正常时）。
3. 裸元件在 DATA 和 3.3V 之间加 4.7k～10k 电阻；模块版一般自带，但可以并联一个 10k 试试。
4. 确认代码：

   ```cpp
   #define DHT_PIN 4
   #define DHT_TYPE DHT22
   ```

   不是 `DHT11`，不是 `DHT21`。
5. 读之间至少 `delay(2000)`。
6. 换一个 GPIO 试（比如 GPIO13），确认不是 GPIO4 的问题。
7. 以上都试过还是 NaN，换一个传感器。DHT22 便宜，但假货/坏件不少。

> 如果只有偶尔 NaN，可能是线太长/电源干扰；加短一点的线、在 VCC-GND 之间并一个 100nF 电容，通常能改善。

## 6. 板子反复重启，串口出现 `Brownout detector was triggered`

**现象：**

```text
Brownout detector was triggered
ets Jun  8 2016 00:22:57
rst:0x1 (POWERON_RESET),boot:0x13
```

板子每隔几秒重启一次，WiFi 刚连上就掉。

**原因：**

**供电不足/电压瞬间跌落。** ESP32 在 WiFi 发射瞬间电流会冲高，如果电源/线材跟不上，电压跌破阈值，芯片就复位。

常见触发场景：

- 用电脑 USB 口 + 细线，带不动 WiFi 峰值电流；
- 继电器吸合瞬间拉低 5V；
- 接了水泵/电机/大电流 LED；
- 用劣质充电头；
- 从 ESP32 的 `3V3` 引脚给继电器线圈或大电流模块供电；
- USB 线太长/太细。

**怎么修：**

1. 换 **5V 1A 以上**的充电头，换短而粗的 USB 数据线，直插墙充，不要用 Hub。
2. 继电器/电机**单独供电**，不要从 ESP32 的 3V3 取电；独立电源的 GND 和 ESP32 GND 连在一起。
3. 在 ESP32 的 5V 和 GND 之间并一个 **100µF～470µF 电解电容**（注意正负极），靠近板子电源脚，能缓冲瞬时跌落。
4. 去掉不必要的负载，先只跑板子 + DHT22，看还重启不重启。
5. 如果是 5V 继电器模块，确认不是由 ESP32 的 3V3 供电；用 5V 供线圈，信号经光耦/三极管。
6. 降低 WiFi 发射功率（临时验证）：

   ```cpp
   WiFi.setTxPower(WIFI_POWER_19_5dBm); // 或更低，如 WIFI_POWER_11dBm
   ```

   发射功率低一点，峰值电流小一点，但信号距离会变短。**先解决供电，不要靠降功率硬撑。**

## 7. 继电器不吸合 / 一直吸合 / 嗒嗒响

**现象：**

- 代码里 `relayOn()` 了，但听不到“嗒”，负载不工作。
- 或者一上电就一直吸合，代码控制不了。
- 或者“嗒嗒嗒”快速响，板子跟着重启。

**原因：**

1. 买的是 **5V 继电器模块**，3.3V GPIO 触发不了。
2. 触发方式搞反：模块是低电平触发，代码按高电平写；或者反过来。
3. VCC/GND 接错、没共地、模块电源灯不亮。
4. 模块是 **JD-VCC 分离**供电，跳线/接线不对。
5. 线圈电流太大，USB 供电掉压，板子重启（见第 6 条）。
6. IN 脚接在了启动脚（GPIO0/2/12/15），上电时电平不对。
7. 模块坏了。

**怎么修：**

1. 看模块电源灯亮不亮；不亮先查 VCC/GND。
2. 确认模块规格：**3.3V 可触发**。5V 模块要么换 3.3V 模块，要么加三极管/光耦驱动，不要硬接。
3. 改代码里的触发方式：

   ```cpp
   #define RELAY_ACTIVE_LOW 1   // 低电平触发
   // 或
   #define RELAY_ACTIVE_LOW 0   // 高电平触发
   ```

   试另一种，看继电器是否动作。
4. 用万用表量 IN 对 GND：
   - 低电平触发：吸合时应接近 0V，断开时接近 3.3V。
   - 高电平触发：反过来。
5. 换到安全 GPIO（如 GPIO26），不要用 GPIO0/2/12/15。
6. 如果是“一直吸合”，在 IN 和 3.3V 之间加一个 **10kΩ 上拉电阻**（低电平触发模块），保证上电默认断开。
7. 继电器单独用 5V 电源，ESP32 和继电器共地；必要时加电容。
8. 还不行就换模块。继电器模块便宜，别跟它死磕。

> 再次提醒：只接低压负载。220V 不要碰。

## 8. 上传成功，但串口没有输出 / 板子像没运行

**现象：**

- IDE 显示 `Hard resetting via RTS pin...`，但串口监视器空白。
- 板载 LED 也不闪。

**原因：**

1. 串口监视器波特率不对。
2. 选错了端口（比如选的是另一个 USB 设备）。
3. 程序卡在 `setup()` 里的 `while` 循环（比如 SHT30 没找到，`while(true)`）。
4. 代码里 `Serial.begin()` 没执行到，或者波特率不是 115200。
5. 板子没复位，还在下载模式。
6. USB 线只能充电（但这种情况通常也上传不了）。

**怎么修：**

1. 串口监视器选 **115200**，按一下 **EN** 键。
2. 确认端口是板子的 COM 口；拔掉其他串口设备再试。
3. 烧回最简单的 `01_blink.ino`，看串口和 LED 是否正常。如果 01 正常，说明问题在后面的代码。
4. 检查代码里有没有 `while (true)`、`while (!WiFi.isConnected())` 这种死循环；有的话，在循环里加 `Serial.println()` 和超时。
5. `setup()` 里第一行就写 `Serial.begin(115200);`，后面加 `delay(500);`，确保串口初始化完成。

## 9. 编译报 `DHT.h: No such file or directory`

**现象：**

```text
fatal error: DHT.h: No such file or directory
```

**原因：**

1. 没装 DHT 库。
2. 装错了库（有多个同名/类似库）。
3. 库装到了另一个 Arduino IDE 版本/用户目录。
4. 开发板包没装好，连带库路径混乱。

**怎么修：**

1. `工具 → 管理库`，搜索 `DHT sensor library`，认准作者 **Adafruit**，安装。
2. 安装时提示依赖 **Adafruit Unified Sensor**，一起装。
3. 装完**重启 Arduino IDE**。
4. 如果之前装过别的 DHT 库，先卸载，避免头文件冲突。
5. 还不行，检查 `文件 → 首选项 → 项目文件夹位置`，确认库装在你当前用的 IDE 目录下。

## 10. 编译报 `multiple definition of setup()` / `loop()`

**现象：**

```text
multiple definition of `setup()'
multiple definition of `loop()'
```

**原因：**

你把多个 `.ino` 放在了同一个文件夹里，Arduino 把它们当成一个项目合并编译了。

**怎么修：**

1. 一个文件夹只放**一个** `.ino`。
2. 用 `文件 → 新建 Sketch`，另存为 `01_blink`，只粘贴 `01_blink.ino` 的内容。
3. 或者给每个实验建独立文件夹：`01_blink/01_blink.ino`、`02_read_sensor/02_read_sensor.ino`。
4. 详见 [code/README.md](code/README.md)。

## 11. HTTPS 连不上 / 证书错误 / `setCACert` 失败

**现象：**

- `setInsecure()` 时能通，换成 `setCACert()` 就不通。
- 串口 HTTP 状态码是负数，或者 `SSL` 相关错误。
- `curl` 能通，ESP32 不通。

**原因：**

1. **ESP32 时间还是 1970 年**，证书“尚未生效”。
2. 根证书不对/不完整/PEM 格式错。
3. 用了 IP 而不是域名，证书域名校验失败。
4. 服务器证书过期/证书链不完整。
5. NTP 被网络屏蔽（UDP 123）。
6. ESP32 内存不足（HTTPS 比 HTTP 吃内存）。
7. 服务器只支持旧 TLS 版本/加密套件，ESP32 不支持。

**怎么修：**

1. 先确认 `setInsecure()` 能通，排除 WiFi/DNS/服务器问题。
2. 加 NTP 对时，循环等到 `time(nullptr) > 1700000000` 再发请求；详见 [04-连上服务器.md](04-连上服务器.md) 第四节。
3. 用**域名** `hopzz.top`，不要用 `64.83.20.24`。
4. 检查根证书：
   - PEM 必须包含 `-----BEGIN CERTIFICATE-----` 和 `-----END CERTIFICATE-----`；
   - 用实际证书链对应的根 CA，不要凭记忆；
   - 不要 pin 90 天就过期的叶子证书。
5. 在 VPS 上 `curl -v https://hopzz.top` 看证书链和有效期；浏览器打开锁图标也能看。
6. 确认网络允许 UDP 123；公司/校园网可能封。
7. 打印 `ESP.getFreeHeap()`，内存太低就减少同时运行的功能。
8. 如果服务器证书链不完整，让 Lead 在 Nginx/Apache 配置里补全中间证书。

> 测试阶段可以继续用 `setInsecure()`，但**上线前必须换掉**。

## 12. POST 返回 401 / 422

**现象：**

```text
HTTP 状态码: 401
服务器响应: {"detail":"设备令牌无效"}
```

或：

```text
HTTP 状态码: 422
```

**原因：**

- `401`：设备令牌缺失/错误，或者服务端没收到 `X-Device-Token`。
- `422`：JSON 字段缺失（例如只发了 `device_id`）、字段名拼错、类型不对、body 不是合法 JSON。

**怎么修：**

1. 先用 `curl` 复现（命令见 [04-连上服务器.md](04-连上服务器.md)），确认服务端本身正常。
2. 看串口打印的 `POST 内容:`，逐字核对：

   ```json
   {"device_id":"esp32-01","temperature":26.5,"humidity":58.2}
   ```

   - `Content-Type` 是不是 `application/json`；
   - 请求头名字是不是 `X-Device-Token`（不是 `Authorization`，不是 `token`）；
   - `DEVICE_TOKEN` 有没有多空格/少字符；
   - `device_id` 是不是服务端认识的；
   - 数字有没有被加上引号；
   - JSON 最后有没有多余逗号。
3. 401 重点查令牌；422 重点查 JSON 字段。两者不要混着改。
4. 让 Lead 看服务端日志里实际收到的 header/body，和串口打印对比。

## 13. OLED / SHT30 / BH1750 的 I2C 设备找不到

**现象：**

- OLED 不亮；SHT30 初始化失败；I2C 扫描不到地址。
- 串口提示“没有找到 SHT30”。

**原因：**

1. SDA/SCL 接反。
2. 模块没供电/没共地。
3. I2C 地址不对（0x3C vs 0x3D，0x44 vs 0x45，0x23 vs 0x5C）。
4. 模块没有上拉电阻，或者多个模块并联后总线异常。
5. 线太长/接触不良。
6. 买错型号（SPI OLED、SH1106 屏）。

**怎么修：**

1. 确认 `VCC→3V3`、`GND→GND`、`SDA→GPIO21`、`SCL→GPIO22`。
2. 跑一个 I2C 扫描程序：

   ```cpp
   #include <Wire.h>

   void setup() {
     Serial.begin(115200);
     Wire.begin(21, 22);
     Serial.println("I2C scan...");
     for (uint8_t addr = 1; addr < 127; addr++) {
       Wire.beginTransmission(addr);
       if (Wire.endTransmission() == 0) {
         Serial.print("found 0x");
         Serial.println(addr, HEX);
       }
     }
   }

   void loop() {}
   ```

   能看到地址，说明总线和供电没问题，再查驱动/地址。
3. 只留一个 I2C 设备测试，排除地址冲突/上拉过强。
4. 线缩短到 20cm 以内；换杜邦线。
5. OLED 买 4 针 I2C、SSD1306；1.3 寸有些是 SH1106，库不一样。
6. SHT30 试 `0x44` 和 `0x45`。

## 14. 板子发烫、闻到焦味、冒烟

**现象：**

- 板子某个芯片/稳压器明显烫手。
- 有焦味、塑料味，或者 USB 口发烫。
- 电脑提示“USB 设备过流”。

**原因：**

1. **5V 接到了 3.3V 引脚或 GPIO**。
2. VCC/GND 接反。
3. 3.3V 和 GND 短路。
4. 传感器/继电器模块电流过大，稳压器过载。
5. 杜邦线金属丝搭在一起。

**怎么修：**

1. **立刻拔 USB！** 不要犹豫，不要“再看一眼”。
2. 不要用手直接摸发烫的芯片；等冷却。
3. 目测有没有明显烧焦、鼓包、连锡。
4. 用万用表通断档量 3V3 和 GND 是否短路；如果是，查线。
5. 重新核对每一根线：5V 只接需要 5V 的模块，GPIO 只接 3.3V 信号。
6. 如果板子已经发烫到烫手/有焦味，**不要再通电**，换板子。ESP32 便宜，别冒险。
7. 以后改线前先拔 USB，这是最便宜的安全习惯。

## 15. 数据不更新 / 网页一直显示旧值

**现象：**

- 串口看起来在跑，但网页上的温湿度一直不变。
- `/api/telemetry/latest` 返回的时间戳很旧。
- 设备每隔 30 秒打印“上报成功”，但网页没变。

**原因：**

1. 设备上报成功，但网页请求的是缓存。
2. 网页读错层/字段（当前服务端是 `{"ok":true,"latest":{...}}`，值在 `latest.temperature` / `latest.humidity`）。
3. 服务端 latest 查询逻辑有问题（取了旧记录）。
4. 设备其实没发出去（串口 200 是上一次的日志，或者你看的是旧串口）。
5. 页面和 API 不同源/CORS，请求失败但页面没提示。
6. 设备时间/服务器时间不一致，显示的时间戳看起来旧。

**怎么修：**

1. 先 `curl -i https://hopzz.top/api/telemetry/latest`，看返回的 JSON 和时间戳是不是新的。**以 curl 为准，不要以网页为准。**
2. 网页 `fetch` 加 `{ cache: 'no-store' }`，或者加时间戳参数（本教程页面已经加了 `no-store`）。
3. 看页面里的“原始返回”，确认字段名；按实际字段改页面。
4. 串口确认每次都有新的 `POST 内容` 和 `HTTP 状态码: 200`，不是卡在循环里。
5. 浏览器 F12 → Network，看 `/api/telemetry/latest` 的状态码和响应；CORS 错误会在 Console 里提示。
6. 找 Lead 查服务端 latest 的查询语句/缓存策略。

## 16. 设备令牌泄露了怎么办

**现象：**

- 令牌被贴到群里、提交到公开 GitHub、写进了前端 JS。
- 发现服务器上有不是你设备发来的假数据。

**原因：**

令牌是设备的“门禁卡”，泄露了别人就能冒充。

**怎么修：**

1. 让服务端**吊销旧令牌，生成新令牌**。
2. 更新设备代码里的 `DEVICE_TOKEN`，重新上传。
3. 如果提交过 Git：
   - 删除仓库里的令牌；
   - 轮换令牌（历史提交里还能看到，删文件不够）；
   - 以后用不提交的 `secrets.h` 或环境变量。
4. 检查服务端日志，看有没有异常 `device_id`/IP 的请求。
5. 前端页面**永远不要**放设备令牌；只读接口不需要令牌。

| 反复重启 | 换 5V 1A 电源、继电器单独供电、加电容 | 第 6 条 |
